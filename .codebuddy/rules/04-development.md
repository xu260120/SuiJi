# 04 - Development Rules

## 开发原则

项目从零开始，不需要为了兼容旧代码而保留旧架构。

开发优先考虑：

- 简单
- 清晰
- 可维护
- 可测试
- 与当前产品规模匹配

默认遵循：

> 理解 → 检查 → 发现问题 → 提出方案 → 最小修改 → 测试 → 如实报告

---

## 最小修改原则

默认采用：

> 能小改就不大改，能复用就不重写。

优先：

1. 修改现有实现
2. 复用已有组件
3. 扩展已有逻辑
4. 在必要时增加新代码

不要为了代码风格而进行没有明确收益的大规模重构。

---

## 修改范围

用户要求：

> 修改功能 A

默认理解为：

> 修改 A 所需要的最小代码范围。

不能自动扩展为：

> 顺便重构 B、C、D。

发现其他问题时，可以报告并建议处理，但不要自动扩大任务范围。

---

## 避免过设计

不要为了“看起来专业”而增加不必要的抽象层。

每增加一个 Service、Manager、UseCase、Factory、Adapter、Mapper 或 Controller，都应能说明其实际解决的问题。

不要仅为了未来可能出现的需求提前建立复杂系统。

---

## 不允许凭空假设

AI 不得假定项目中存在：

- 某个文件
- 某个 Class
- 某个方法
- 某个 API
- 某个数据库字段
- 某个依赖
- 某个组件
- 某个路由

必须先检查实际项目。

---

## 优先检查

开始修改前，根据任务需要检查：

- 项目目录
- 相关源码
- 调用关系
- 数据模型
- 状态管理
- 相关测试
- 相关配置
- Design Token（路径与权威说明见 `09-design.md`）
- Git 状态
- 当前修改
- Monekin 参考实现（只读参考目录，不复制代码）

---

## 保护用户代码

如果发现用户已经修改但尚未提交：

不得擅自：

- 覆盖
- 删除
- 重置
- 回滚

必须尽量在现有修改基础上继续工作。

---

## 不确定时

如果无法确定某个实现：

第一步：

> 检查代码。

第二步：

> 检查调用关系和相关文件。

第三步：

> 检查 Git 历史，或查阅 Monekin 参考目录理解设计思路（只读，不复制代码）。

仍然无法确定：

> 明确告诉用户目前无法确认。

禁止用猜测代替事实。

---

## 重构

大规模重构需要明确理由。

例如：

- 当前架构已经无法支持需求
- 存在严重数据问题
- 存在严重维护问题
- 用户明确要求重构

不能仅因为：

> “这样写更优雅。”

就重构整个模块。

大规模架构调整必须说明：为什么调整、影响哪些模块、为什么当前架构无法满足需求、如何验证调整结果。

---

## 依赖

添加第三方依赖前，应判断：

- 是否真的需要
- 是否可以使用 Flutter 原生能力
- 是否维护活跃
- license
- API 稳定性
- 对复杂度和构建体积的影响

添加前还应按 `08-ai-behavior.md`「版权与许可：第一时间告知」主动告知用户许可风险，不得等到依赖添加完成后才说明；该依赖作为非自主开发内容，按同文件「非自主开发内容的参考来源」在报告中标注来源。

添加后必须说明原因和影响。

---

## 无隐藏改动

不得顺手修改与当前任务无关的产品、设计、数据或配置。

发现相关问题可以提出，但不要未经授权扩大任务范围。

---

## 修改后的说明

完成修改后按 `11-change-control.md` 的统一报告格式说明变更，本节不另设报告字段。

其中「为什么修改」「是否涉及其他模块」在报告的「变更范围」或「风险 / 问题」里如实交代，不得省略。
